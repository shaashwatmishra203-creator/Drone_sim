# 08 — Factory Navigation and Mapping Mission

> **Verification level: L0–L2.** Simulation only. Masses still estimated.

The representative mission, flown end to end in PX4 SITL: launch from base,
navigate a slalom obstacle course through a factory-like environment, scan a
room at the far end, return to base and land.

---

## The environment

`worlds/factory.sdf`, generated by `tools/gen_world.py` so the obstacle layout
lives in version control rather than in a hand-edited XML file.

```
   y
   |   [rack]        [rack]                +---------------+
   |            [rack]        [rack]       |               |
 --+---O--------|--------|--------|------- |     ROOM      |  <- scan here
   |  base   [pillar] [pillar] [pillar]    |   12 x 12 m   |
   |                                       +---------------+
   0        8   10  12  14  16 ... 22      26      32      (x, metres)
```

| Feature | Detail |
|---|---|
| Launch base | 2.4 × 2.4 m pad at the origin. **Visual only, no collision body** |
| Storage racks | 4, alternating at y = ±3.2 m, 3 m tall, forcing lateral movement |
| Pillars | 4, on the centreline at x = 10/14/18/22 m, 0.45 m square, 4 m tall |
| Room | 12 × 12 m, 4 m tall, four walls with a 4 m doorway on the −x face |
| Room contents | Two crates and a machine, so a scan has real geometry to map |
| Clearance | ≈3 m gaps against a 0.5 m airframe — 1.25 m from centreline to obstacle |

The launch pad being visual-only matters. An early version gave it a collision
box; the vehicle spawned against it and spent **88 seconds at 2.4 kW fighting
the ground** before breaking free, burning 34 Wh and wrecking the mission energy
accounting. A launch base is a painted floor marking, and modelling it as one
removed the problem entirely.

## The mission profile

`scenarios/factory_mission.yaml`, flown by the `factory_mission` profile added
to `mission_runner`. Four legs, each timed separately:

1. **Outbound** — 11 waypoints threading the slalom, yawing to face the
   direction of travel so the cameras look where the aircraft is going.
2. **Scan** — an 8-point lawnmower sweep inside the room at 2.2 m with a
   continuous 0.35 rad/s yaw sweep, covering walls, floor and objects. This is
   the motion a real mapping pass would fly.
3. **Inbound** — retrace the course back to base.
4. **Land** — descend onto the pad.

Light wind (1.5 m/s with 0.8 m/s gusts) is applied after takeoff — an indoor
factory is not still air, but it is not open sky either.

> The scan leg measures what a mapping pass **costs** in time and energy. It
> does not build an actual map: that needs the ZED SDK, which requires CUDA and
> does not run in SITL. See [09-compute-architecture.md](09-compute-architecture.md).

## Results

Flown with the current parts list — 9×4.5 props, Pi 5 mass and power, estimated
3.12 kg AUW.

| | |
|---|---:|
| **Airborne time** | **62.2 s (1.04 min)** |
| Mission legs | 57.4 s |
| Path flown | 108.6 m |
| Mean speed | 1.76 m/s (peak 3.42) |
| Mean power | 630.8 W (peak 1573) |
| **Energy used** | **10.90 Wh** of 107 Wh usable |
| Pack remaining on touchdown | **92.2%** |
| Energy per metre | 100.4 mWh/m |

### Leg breakdown

| Leg | Time (s) | Share |
|---|---:|---:|
| Outbound (obstacle course) | 18.5 | 32.2% |
| Scan (mapping pass) | 17.5 | 30.5% |
| Inbound (return to base) | 20.3 | 35.4% |
| Land | 1.1 | 1.9% |
| **Total** | **57.4** | |

The mapping pass is about **30% of the mission** — comparable to either transit
leg. That is worth knowing: scanning is not a cheap add-on at the end, it is a
third of the flight.

### Operational margin

| | |
|---|---:|
| Usable energy consumed | 10.2% |
| Reserve above the DoD gate | 90.2% |
| **Round trips per charge** | **9.8** |

**Verdict: comfortable.** One pack supports nearly ten of these missions. The
mission is short relative to the aircraft's ~11 minute endurance, so endurance
is not the binding constraint for this particular task — which is a different
conclusion from the hover tests, and a more useful one operationally.

## What this does and does not establish

**Does:** the aircraft can fly a realistic obstacle course at survey speed,
hold a scan pattern, and return to base with very large energy reserve. The
mission is well within the airframe's capability even on the current
(sub-optimal) 9-inch propellers.

**Does not:**

- **No actual obstacle avoidance was tested.** The waypoints are pre-planned
  and collision-free by construction. The vehicle flew a known-good path; it
  did not perceive the racks and decide to avoid them. Closing that gap needs
  the depth pipeline, which needs CUDA hardware — see
  [09-compute-architecture.md](09-compute-architecture.md).
- **No map was produced.** The scan leg measures the cost of the motion, not
  the quality of the result.
- **Speed is conservative.** 1.76 m/s mean was chosen as a survey speed. The
  compute analysis shows what the ceiling would be with real perception in
  the loop.

## Reproducing

```bash
python3 tools/gen_world.py --out worlds/factory.sdf
```

```bash
bash scripts/run_scenario.sh scenarios/factory_mission.yaml 9x4.5 pi5
```

```bash
python3 tools/analyze_mission.py
```

To watch it fly:

```bash
GUI=1 bash scripts/run_scenario.sh scenarios/factory_mission.yaml 9x4.5 pi5
```
